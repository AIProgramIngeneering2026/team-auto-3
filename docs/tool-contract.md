# Контракт исполнителя (Analyzer)

Исполнитель — анализатор. Единый интерфейс для моделей на transformers, правил
и любых будущих реализаций, включая LLM-сводку второго семестра.

```python
from typing import Protocol

class Analyzer(Protocol):
    name: str            # "sentiment" | "aspect" | "suspicion" | "verdict"

    def analyze(self, reviews: list[Review]) -> AnalyzerResult:
        """Обработать пачку отзывов одного отчёта."""
```

Входные и выходные структуры:

```python
@dataclass(frozen=True)
class Review:
    external_id: str          # идентификатор отзыва в источнике
    positive_part: str        # Positive_Review, служебные строки уже вырезаны
    negative_part: str        # Negative_Review, служебные строки уже вырезаны
    author_score: int         # оценка автора 1..10 из источника
    days_since: int           # days_since_review из источника

@dataclass(frozen=True)
class Finding:
    external_id: str          # к какому отзыву относится
    kind: str                 # "sentiment" | "aspect" | "suspicion"
    value: dict               # {"stars": 3} | {"aspect": "food"} | {"rule": "burst"}

@dataclass(frozen=True)
class AnalyzerResult:
    analyzer: str             # имя анализатора
    findings: list[Finding]   # находки по каждому отзыву, где они есть
    skipped: list[str]        # external_id отзывов, которые анализатор не осилил
```

Границы контракта:

- **Кто проверяет параметры.** Входные данные готовит и проверяет конвейер,
  не анализатор: нормализация («No Negative»/«No Positive» вырезаны, типы верные).
  Анализатор получает гарантированно валидный список и не делает повторной валидации.
  Свои настройки (порог уверенности, окно времени) анализатор держит у себя
  и получает из конфигурации, не из параметров вызова.
- **Ошибки.** Ожидаемые отказы анализатор возвращает как `skipped`, не исключениями:
  пустой текст после нормализации, текст не на поддерживаемом языке, уверенность
  ниже порога. Исключение из анализатора — это баг: конвейер падает в `failed`
  с internal_error, повтора не предусматриваем.
- **Чистота.** Анализатор не знает про HTTP, БД и состояния Job; не ходит в сеть
  (веса моделей уже скачаны к моменту вызова); не пишет логи напрямую — возвращает
  результат, логирует конвейер.
- **Регистрация.** Исполнитель попадает в AnalyzerRegistry записью «имя → класс».
  Dispatcher берёт анализаторы по имени и не знает конкретных классов; новый
  анализатор добавляется без правки Dispatcher.

## Два исполнителя через этот контракт

### SentimentAnalyzer (модель)

- `name = "sentiment"`.
- Готовая многоязычная модель тональности со шкалой 1–5 (nlptown) через
  transformers pipeline. Веса качаются при старте, ревизия запинена.
- Вход: `Review` целиком — положительная и отрицательная части оцениваются
  отдельно. Выход: `Finding(kind="sentiment", value={"stars": 1..5})` на каждую
  непустую часть отзыва.
- Отказы как `skipped`: обе части пусты после нормализации; язык не из
  поддерживаемых.
- Проверка качества: параметризованный тест на отзывах с известной `author_score`
  из датасета, сходимость в пределах ±1 звезды на срезе.

### SuspicionAnalyzer (правила)

- `name = "suspicion"`.
- Чистые правила, без моделей: аномальная плотность максимальных оценок в окне
  N дней; однотипные сверхкороткие тексты; точные дубли текстов.
- Вход: список всех отзывов организации сразу (правила смотрят на распределение,
  не на отдельный отзыв). Выход: `Finding(kind="suspicion", value={"rule": ...})`
  на каждый подозрительный отзыв.
- Отказы как `skipped`: отзывов в пачке меньше трёх — правила на таком объёме
  не имеют смысла.
- Детерминированность: одинаковый вход даёт одинаковый выход, это опора
  негативных тестов.
