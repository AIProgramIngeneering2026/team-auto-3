# Проверка контракта колодой (К1–К10)

Контракт: `docs/api/openapi.yaml`, схемы состояний: `docs/architecture.md`,
решения: `docs/adr/`.

| Карта | Ответ контракта |
|---|---|
| К1 Двойной клик | Один Job. Повтор `POST /reports` с тем же `Idempotency-Key` и тем же телом → `200` с прежним `report_id` и текущим статусом, выполнения нет — `openapi.yaml`, `POST /reports`, и ADR-0002 |
| К2 Ответ потерялся | Клиент повторяет запрос тем же ключом и получает уже созданный отчёт со статусом; статус всегда доступен через `GET /reports/{id}` — ADR-0002, ADR-0001 (фоновый запуск, ответ сервера короткий) |
| К3 Неизвестная операция | Нет такого пути/метода — `404` от роутинга FastAPI, Job не создаётся. Бизнес-операций с «неизвестным именем» в API нет: набор фиксированный, см. `openapi.yaml`, paths. Сознательно не создаём отдельного кода: студент с curl увидит стандартный ответ фреймворка |
| К4 Кривые параметры | `400 invalid_params`, в `details.fields` поимённо, какое поле и что не так (`organization_id: обязательное поле`, `limit: должно быть от 1 до 50`) — `openapi.yaml`, responses.BadRequest |
| К5 Воскрешение | Запуск завершившегося отчёта запрещён: любые переходы из `done/partial/insufficient/failed/cancelled` → `409 invalid_transition`, состояние не меняется — `openapi.yaml`, `POST /reports/{id}/cancel`, architecture.md. Нужен новый разбор — новый `POST /reports` (новый ключ или тот же ключ с тем же телом вернёт прежний отчёт) |
| К6 Отмена | `POST /reports/{id}/cancel` из `created/collecting/analyzing` → `cancelled`; частичная работа не выдаётся, вердикт не строится — requirements.md, сценарий 6. Из конечных состояний — `409 invalid_transition` |
| К7 Огромный вход | Отзывов у организации в датасете максимум пара тысяч, «вход» задаётся идентификатором, не телом: раздуть запрос нельзя. Ограничения на клиентские параметры есть (`limit ≤ 50`, ключ ≤ 64) — `openapi.yaml`, parameters. Неприменимо в полной мере, зафиксировано здесь |
| К8 Чужой или несуществующий id | Несуществующий отчёт → `404 report_not_found`; перечисления чужих отчётов в API нет, идентификаторы не угадываются — `openapi.yaml`, responses.ReportNotFound. Аутентификации в версии нет, «чужого» не существует: API один общий, сознательное ограничение |
| К9 Перезапуск сервера | Job в промежуточном состоянии (`created/collecting/analyzing`) при старте помечается `failed` с `reason=error`, перезапуск не «воскрешает» работу; клиент видит причину в `GET /reports/{id}` и создаёт отчёт заново — ADR-0001, цена решения. Ключ идемпотентности сохранён, повтор тем же ключом вернёт упавший отчёт без дубля |
| К10 Внешний сервис | До трёх повторов на страницу на таймаут и 5xx; часть страниц не пришла → `partial` с `coverage`; всё упало → `failed source_unavailable`; мусорный ответ разбирается как «страница не получена» — requirements.md, сценарий 5, ADR-0001 |

Строк «не знаем» и «потом» в таблице нет. Сознательно не закрываем: К8 в части
«чужих данных» — аутентификации нет, API без клиентов-владельцев (это учебный
сервис и требованием не предусмотрена).

## Что предложил ИИ

Промпт (модель GLM-5.3, ассистент ZCode):

> Вот OpenAPI-контракт сервиса «Вердикт»: POST /reports с Idempotency-Key
> (повтор с тем же телом — 200 с прежним отчётом, с другим телом — 409),
> GET /reports/{id} со статусами done/partial/insufficient/failed/cancelled,
> POST /reports/{id}/cancel только из промежуточных состояний, GET /organizations.
> Сыграй атакующего из контрактного покера: найди 3 ситуации, на которые этот
> контракт не отвечает. Формат: ситуация, что спросит атакующий, чего в контракте
> нет.

Предложения и решения:

1. **Отчёт отменяют на границе этапов.** Отмена приходит, когда Job уже перешёл
   из `collecting` в `analyzing`, но ответ на cancel ещё не отправлен — кто
   прав, `cancelled` или `analyzing`?
   Приняли: в контракт добавили уточнение — отмена выполняется как переход
   состояния с проверкой текущего; если Job уже в `analyzing`, отмена всё равно
   легальна (analyzing — промежуточное), а вот из конечного — `409`. В
   architecture.md это уже отражено.
2. **К1 × К5: тот же ключ после падения.** Отчёт упал в `failed`, клиент
   повторяет запрос с тем же ключом и тем же телом — что вернётся, упавший
   отчёт или новый?
   Приняли: в ADR-0002 явно написано — возвращается прежний отчёт со статусом
   `failed`, нового Job нет. Клиент, желающий перезапуска, обязан взять новый
   ключ. Было несказано, теперь зафиксировано.
3. **trend=unknown и недостаточность данных.** Вердикт готов, но отзывы есть
   только за последний месяц — тренду неоткуда взяться. Контракт не отвечал,
   отдавать ли `unknown` или валить отчёт в `insufficient`.
   Приняли: добавили значение `unknown` в enum тренда (`openapi.yaml`, Verdict);
   `insufficient` оставили только для нехватки отзывов вообще. Причина различия:
   аспектные оценки на месячном окне валидны, тренд — нет.
