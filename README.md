# Вердикт

Сервис разбирает отзывы об организации и отвечает, нормально ли туда идти, чтобы
человек не вычитывал сотни отзывов руками.

У популярного отеля отзывов много. Половина противоречит другой половине, часть
накручена, а до конца доходит редко. В итоге решение принимается по двум последним
отзывам, то есть наугад.

Как работает: клиент называет организацию, сервис забирает её отзывы из источника,
прогоняет через анализаторы и отдаёт вердикт. Внутри вердикта оценки по аспектам
(еда, сервис, чистота, расположение, цена), тренд по времени и два рейтинга: общий
и посчитанный без отзывов, подозрительных на накрутку.

## Для кого

Гости, которые выбирают отель или место. Аналитики и сторонние сервисы, которым
нужен разбор через HTTP API. Сами организации: по вердикту видно, что именно просело.

## Данные

Открытый датасет [515K Hotel Reviews](https://www.kaggle.com/datasets/jiashenliu/515k-hotel-reviews-data-in-europe)
(Booking.com, Европа): 515 738 отзывов о 1 493 отелях. Организация в сервисе — отель
из этого набора. У каждого отзыва отдельно записаны плюсы и минусы, есть оценка автора
и давность, из этого получаются аспектный анализ, проверка сентимент-модели и тренды.

Датасет не читается файлом из ядра. Он развёрнут отдельным сервисом-источником
с HTTP API и пагинацией, как внешний Booking-подобный API.

## Что входит

- поиск организации по названию и городу;
- отчёт-задача с жизненным циклом `created → collecting → analyzing → done /
  partial / insufficient / failed / cancelled`;
- анализаторы за общим контрактом `Analyzer`:
  - `SentimentAnalyzer` — готовая многоязычная модель тональности, шкала 1–5;
  - `AspectAnalyzer` — zero-shot отнесение фрагмента отзыва к аспекту;
  - `SuspicionAnalyzer` — правила поиска накрутки: плотность пятёрок в коротком
    окне времени, однотипные короткие тексты;
  - `VerdictComposer` — сборка вердикта: аспектные оценки, затухание по времени,
    рейтинг без подозрительных отзывов;
- REST API (OpenAPI), идемпотентное создание отчёта, ошибки в одном формате;
- источник с управляемыми отказами (таймаут, 500, мусорный ответ) для тестов
  и демонстрации деградации.

## Что не входит

Обучение своих ML-моделей не делаем, берём готовые. UI, деплой в облако
и рекомендации «похожие отели» — за рамками.

Парсинг живых Booking.com или Яндекс.Карт в первой версии не делаем: для курса
важнее воспроизводимые отказы источника и запуск из чистого клона. Архитектурно
запрета нет: источник — отдельный провайдер за контрактом адаптера, и реальный
сайт подключился бы как ещё одна реализация рядом с датасетной.

## Стек

Python 3.13, FastAPI, SQLAlchemy 2 + Alembic (SQLite, позже PostgreSQL), httpx,
transformers (сентимент и zero-shot), structlog, pytest, Docker Compose,
GitHub Actions.
